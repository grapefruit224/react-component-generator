# commit: 변경사항 분석 → 논리 단위 커밋

변경사항을 읽고, 리뷰어가 커밋 하나하나를 독립적으로 이해할 수 있도록 **논리적 단위**로 나눠 커밋한다. 커밋은 되돌리기 번거로운 작업이므로 **계획을 보여주고 승인을 받은 뒤에만** 실행한다.

## Step 0: 저장소 지침 확인

저장소 루트의 `AGENTS.md`/`CLAUDE.md`에 커밋 관련 규칙(타입 목록, scope, trailer, 언어 등)이 있으면 그것이 이 문서보다 우선한다. 없으면 아래 컨벤션을 쓴다.

## Step 1: 변경사항 수집

아래를 실행해 전체 그림을 먼저 파악한다. `git diff`만으로는 **새 파일(untracked)과 이미 stage된 변경이 보이지 않기 때문에** 세 가지를 모두 본다.

```bash
git status --short
git diff --staged      # 이미 stage된 변경
git diff               # stage 안 된 변경
git log --oneline -10  # 기존 커밋 스타일 참고 (커밋이 아직 없으면 실패해도 정상)
```

- untracked 파일은 `git status`로 목록을 확인하고, 필요하면 내용을 직접 읽어 무엇인지 파악한다.
- diff가 매우 크면 `git diff --stat`으로 범위를 먼저 보고, 판단에 필요한 파일만 자세히 읽는다. lock 파일(`bun.lock`, `package-lock.json` 등)이나 빌드 산출물은 내용 대신 "의존성 변경"처럼 성격만 파악하면 충분하다.
- 변경사항이 하나도 없으면 그렇게 알리고 종료한다.

### 사용자가 이미 stage해 둔 경우

사용자가 일부 파일만 stage해 뒀다면 그것이 의도일 가능성이 높다. 계획을 세울 때 "stage된 것만 커밋할지, 전체를 나눠 커밋할지" 물어본다.

### 커밋하면 안 되는 것

다음이 변경 목록에 보이면 계획에서 제외하고 사용자에게 따로 알린다. 한번 커밋된 비밀값은 히스토리에 남아 제거가 어렵기 때문이다.

- `.env`, `*.pem`, `*.key`, `credentials*`, API 키·토큰이 하드코딩된 diff
- `node_modules/`, `dist/` 등 `.gitignore`에 있어야 할 산출물
- 디버깅용 임시 코드(`console.log` 남발, 주석 처리된 대량 코드)는 제외까지는 아니어도 계획에 "확인 필요"로 표시한다.

## Step 2: 논리적 단위로 분류

기준은 **"이 커밋 하나만 revert해도 의미가 통하는가"**다.

- 하나의 기능·버그 수정에 속한 코드, 그 테스트, 관련 타입 변경은 **한 커밋**으로 묶는다. 테스트를 별도 커밋으로 떼지 않는다.
- 성격이 다른 변경(기능 추가 + 무관한 리팩터링 + 설정 변경)은 나눈다.
- 반대로 과하게 쪼개지 않는다. 파일 하나당 커밋 하나는 대부분 잘못 나눈 것이다. 변경이 하나의 목적이면 커밋도 하나면 된다.
- 기본은 **파일 단위**로 나눈다. 한 파일 안에 성격이 다른 변경이 섞여 있을 때만 hunk 단위 분리를 고려한다(아래 "부분 stage" 참고). 분리가 어렵거나 위험하면 한 커밋으로 묶고 그 이유를 계획에 적는다.
- 커밋 순서는 의존 관계를 따른다. 나중 커밋이 앞 커밋 없이 빌드가 깨지지 않도록, 기반(설정·타입·유틸)을 먼저 둔다.

## Step 3: 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<본문 (선택)>
```

**type** — 아래 네 가지만 쓴다.

| type | 언제 |
|---|---|
| `feat` | 사용자가 체감하는 새 기능·동작 추가 |
| `fix` | 버그 수정, 잘못된 동작 교정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서, 스크립트 등 그 외 |

애매하면 "사용자 관점에서 동작이 바뀌는가?"로 판단한다. 바뀌면 feat/fix, 아니면 refactor/chore. 문서·README 변경은 `chore`로 둔다.

**요약** 작성 규칙:

- 한국어, 50자 내외, 끝에 마침표 없음
- "무엇을 했는가"가 드러나는 명사형 종결: `~ 추가`, `~ 수정`, `~ 분리`, `~ 제거`
- 파일명 나열 대신 의도를 쓴다: `fix: App.tsx 수정` ✗ → `fix: 미리보기 새로고침 시 이전 코드가 남는 문제 수정` ✓
- 코드 식별자(함수명, 패키지명)는 원문 그대로 둔다.

**본문**은 요약만으로 "왜"가 전달되지 않을 때만 쓴다. 변경 이유, 주의점, 영향 범위를 짧은 bullet로 적는다. 자명한 커밋에 본문을 억지로 붙이지 않는다.

**예시**

```
feat: Gemini 프로바이더 선택 기능 추가

- 서버 프록시에 /api/gemini 엔드포인트 추가
- UI 드롭다운에서 Claude/Gemini 전환 가능
```

```
refactor: 프롬프트 빌더를 별도 모듈로 분리
```

```
chore: 초기 프로젝트 구성
```

환경이나 저장소 지침이 요구하는 trailer(예: `Co-Authored-By:`)가 있으면 본문 맨 끝에 빈 줄을 두고 붙인다.

## Step 4: 계획 제시 및 승인

커밋하기 전에 아래 형식으로 계획을 보여주고 **멈춘다**. 사용자의 명시적 승인("ㅇㅇ", "진행", "좋아" 등) 전에는 `git add`/`git commit`을 실행하지 않는다.

```
커밋 계획 (총 N개)

1. feat: Gemini 프로바이더 선택 기능 추가
   - server/providers/gemini.ts (신규)
   - src/components/ProviderSelect.tsx

2. chore: eslint 규칙 정리
   - eslint.config.js

제외: .env (비밀값 포함 가능), debug.log
확인 필요: src/App.tsx 에 console.log 3개 남아 있음

진행할까요? 메시지 수정·묶음 변경도 말씀해 주세요.
```

사용자가 수정을 요청하면 계획을 고쳐 다시 보여주고 다시 승인을 받는다. 사용자가 처음부터 "묻지 말고 바로 커밋해" 처럼 명시했다면 이 단계에서 멈추지 않아도 되지만, 계획은 그대로 출력해 무엇이 커밋되는지 남긴다.

## Step 5: 커밋 실행

승인된 계획을 순서대로 실행한다.

1. 시작 전 `git reset`으로 index를 비우지 **않는다**. 사용자가 stage해 둔 상태를 존중해야 하므로, 계획이 전체 커밋이라면 각 커밋마다 해당 파일만 명시적으로 `git add <경로...>` 한다. 계획과 무관하게 이미 stage된 파일이 있으면 먼저 `git restore --staged <경로>`로 해당 파일만 내린다.
2. `git add -A`, `git add .`은 쓰지 않는다. 제외 대상 파일이 섞여 들어가기 쉽다.
3. 커밋 메시지는 여러 줄이 깨지지 않도록 heredoc으로 전달한다.
   ```bash
   git commit -F - <<'EOF'
   feat: Gemini 프로바이더 선택 기능 추가

   - 서버 프록시에 /api/gemini 엔드포인트 추가
   EOF
   ```
4. 커밋마다 `git status --short`로 의도한 파일만 들어갔는지 확인한다.
5. pre-commit hook이 실패하면 `--no-verify`로 우회하지 않는다. 원인을 사용자에게 보여주고, 고칠 수 있으면 고친 뒤 **새로** 커밋한다(`--amend`는 이전 커밋을 바꿔버리므로 쓰지 않는다).
6. push는 하지 않는다. 사용자가 요청하면 그때 별도로 한다.

### 부분 stage (한 파일 안의 변경을 나눌 때)

`git add -p`는 대화형이라 이 환경에서 쓸 수 없다. 대신 해당 hunk만 담은 patch 파일을 만들어 `git apply --cached <patch>`로 stage한다. 적용 후 `git diff --staged <파일>`로 원하는 부분만 올라갔는지 반드시 확인한다. 실패하거나 결과가 불확실하면 파일 단위로 묶는 쪽으로 물러선다.

## Step 6: 결과 보고

마지막에 `git log --oneline -N`(N = 이번에 만든 커밋 수)을 보여주고, 커밋하지 않고 남겨둔 파일이 있으면 함께 알린다.
