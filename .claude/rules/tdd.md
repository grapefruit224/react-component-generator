# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 적용 대상이면 예외 없이 아래 사이클을 따른다.

## 0. 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그것이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 적용되는 **기본값(fallback)**이다.

## 1. 적용 기준

**TDD 필수**

- 비즈니스 로직 (도메인 규칙, 상태 전이, 계산)
- API (엔드포인트, 요청/응답 처리, 에러 처리)
- 유틸 함수 (파서, 변환기, 포매터, 검증기)
- **버그 수정** — 버그를 재현하는 실패 테스트부터 작성한다

**TDD 불필요**

- 타입 정의 (`interface`, `type`, 선언 파일)
- 설정 파일 (빌드, 린트, tsconfig, 환경 설정)
- 순수 UI (로직 없는 마크업·스타일)
- SQL (스키마, 마이그레이션, 쿼리 문자열 자체)

> UI 안에 로직(조건 분기, 상태 관리, 이벤트 처리)이 있으면 **그 로직은 TDD 대상**이다.

## 2. RED → GREEN → REFACTOR

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트를 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"**이어야 한다.
  - 문법 오류, import 오류, 오타, 잘못된 테스트 설정으로 인한 실패는 RED가 아니다 → 고치고 다시 실행한다.

### GREEN — 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI** — 테스트가 요구하지 않는 분기·옵션·일반화를 미리 넣지 않는다.
- **신규 테스트 + 기존 테스트 전부** 통과를 확인한다. 하나라도 깨지면 GREEN이 아니다.

### REFACTOR — 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 돌려 **green을 유지**한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 다음 RED로 간다.

### 반복

- 다음 동작을 하나 골라 **RED로 돌아간다.**

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 다시 시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일, 다른 브랜치에 보관하는 것도 모두 금지다.
- 먼저 쓴 코드를 보며 테스트를 맞추면 테스트가 구현을 따라가게 된다. 테스트가 설계를 이끌어야 한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 1분이면 끝난다. 단순한 코드일수록 경계값에서 깨진다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 사후 테스트는 구현을 검증하지 않고 구현을 복사한다. |
| "시간이 없다" | 디버깅과 회귀 수정에 드는 시간이 더 크다. TDD는 시간을 아끼는 방법이다. |
| "삭제하면 낭비" | 매몰 비용이다. 다시 쓰는 코드는 더 빠르고 더 낫다. 테스트 없는 코드를 남기는 게 진짜 낭비다. |
| "프로토타입이다" | 프로토타입은 거의 항상 프로덕션이 된다. 정말 버릴 코드라면 적용 대상 판단부터 다시 하고, 대상이면 TDD를 따른다. |
